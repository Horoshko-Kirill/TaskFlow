# Отчёт по проекту TaskFlow

## 1. Доменная область

**TaskFlow** — клиент-серверное приложение для управления проектами и задачами.

Приложение предназначено для командной работы над несколькими проектами. Пользователь может создавать проекты, участвовать в существующих проектах, просматривать задачи, назначать задачи участникам проекта и отслеживать их выполнение.

Основной рабочий процесс приложения выглядит следующим образом:

1. Пользователь создаёт проект.
2. В проект добавляются участники.
3. Для проекта создаются задачи.
4. Задачи назначаются участникам.
5. Участники изменяют состояние задач.
6. Задачи перемещаются между колонками Kanban-доски.
7. К задачам добавляются комментарии.
8. Пользователь может отдельно просматривать задачи, назначенные ему.

# 3. Основные сущности

## User

Пользователь системы.

Основные поля:

* `Id`;
* `Name`;
* `Email`;
* `CreatedAt`.

Пользователь может участвовать в нескольких проектах, быть назначенным исполнителем задач и оставлять комментарии.

## Project

Проект, в рамках которого выполняются задачи.

Основные поля:

* `Id`;
* `Name`;
* `Description`;
* `CreatedAt`.

Проект содержит участников и задачи.

## ProjectMember

Связь пользователя с проектом.

Содержит:

* `ProjectId`;
* `UserId`;
* `JoinedAt`.

Позволяет одному пользователю участвовать в нескольких проектах, а одному проекту иметь нескольких участников.

## Task

Основная рабочая сущность приложения.

Основные поля:

* `Id`;
* `ProjectId`;
* `AssigneeId`;
* `Title`;
* `Description`;
* `Status`;
* `Priority`;
* `CreatedAt`;
* `DueDate`.

Для задачи поддерживаются статусы:

* `Todo`;
* `InProgress`;
* `Done`.

Приоритеты:

* `Low`;
* `Medium`;
* `High`;
* `Critical`.

## Comment

Комментарий к задаче.

Основные поля:

* `Id`;
* `TaskId`;
* `AuthorId`;
* `Text`;
* `CreatedAt`.

Комментарии позволяют участникам проекта обсуждать конкретную задачу.

# 4. Методология Twelve-Factor App

Проект реализован с учётом принципов **Twelve-Factor App**.

## 1. Codebase — одна кодовая база

Исходный код приложения хранится в одной кодовой базе.

Backend и frontend находятся в рамках одного проекта TaskFlow:

```text
TaskFlow/
├── src/
└── frontend/
```

При необходимости приложение может быть развёрнуто из одной кодовой базы в разных окружениях.

---

## 2. Dependencies — зависимости

Все зависимости приложения явно описаны средствами соответствующих систем управления пакетами.

Для backend используются NuGet-пакеты, информация о которых хранится в:

```text
*.csproj
```

Для frontend используются npm-зависимости:

```text
package.json
package-lock.json
```

Таким образом, зависимости не устанавливаются вручную и могут быть восстановлены автоматически во время Docker-сборки.

---

## 3. Config — конфигурация

Конфигурация, зависящая от окружения, не должна быть жёстко зашита в исходный код backend.

Для PostgreSQL используются переменные окружения:

```text
POSTGRES_DB
POSTGRES_USER
POSTGRES_PASSWORD
```

Docker Compose передаёт параметры подключения к базе данных через:

```text
Database__ConnectionString
```

Пример локальной конфигурации хранится в:

```text
.env.example
```

Файл `.env` предназначен для локальных значений окружения и не должен содержать реальные секреты в репозитории.

---

## 4. Backing Services — внешние сервисы

PostgreSQL рассматривается как отдельный backing service приложения.

Backend не содержит встроенную базу данных. Подключение выполняется через строку подключения, переданную через конфигурацию окружения.

В Docker Compose PostgreSQL запускается отдельным контейнером:

```text
TaskFlow.db
```

Это позволяет заменить экземпляр базы данных без изменения бизнес-логики приложения.

---

## 5. Build, Release, Run

Для сборки и запуска приложения используются Docker-образы.

Backend собирается в отдельный образ.

Frontend сначала собирается Angular CLI, после чего статические файлы помещаются в Nginx image.

Миграции базы данных также собираются в отдельный образ.

Запуск выполняется через:

```cmd
docker compose up --build -d
```

Таким образом, стадии сборки и запуска отделены друг от друга.

---

## 6. Processes — процессы

Backend запускается как отдельный stateless-процесс.

Состояние приложения не хранится в памяти процесса как единственный источник данных. Основные данные находятся в PostgreSQL.

Frontend также не хранит серверное состояние внутри Nginx.

Благодаря этому отдельные экземпляры API могут запускаться независимо друг от друга.

---

## 7. Port Binding — привязка портов

Приложение предоставляет сервисы через собственные HTTP-порты.

Backend:

```text
8080
```

Frontend:

```text
80
```

Frontend взаимодействует с backend через HTTP REST API.

---

## 8. Concurrency — масштабирование процессов

Архитектура backend не требует хранения пользовательского состояния в памяти конкретного экземпляра API.

Основные данные хранятся в PostgreSQL.

Поэтому при необходимости приложение может быть запущено в нескольких экземплярах backend за балансировщиком нагрузки.

Например:

```text
          ┌── TaskFlow API #1 ──┐
Client ───┼── TaskFlow API #2 ──┼── PostgreSQL
          └── TaskFlow API #3 ──┘
```

Каждый экземпляр API использует одну внешнюю базу данных.

---

## 9. Disposability — готовность к остановке и запуску

Приложение запускается в Docker-контейнерах, что позволяет быстро создавать и удалять экземпляры процессов.

Backend не требует сохранения локального состояния контейнера для восстановления данных.

Данные PostgreSQL вынесены в Docker volume:

```text
postgres_data
```

Поэтому удаление контейнера API не приводит к удалению данных приложения.

Отдельный контейнер миграций выполняет свою задачу и завершается после успешного применения миграций.

---

## 10. Dev/Prod Parity — соответствие окружений

Для запуска приложения используется контейнеризация.

Основные компоненты приложения запускаются одинаковым способом:

* PostgreSQL;
* backend;
* frontend;
* миграции.

Docker Compose позволяет воспроизводить окружение на другой машине без необходимости вручную устанавливать PostgreSQL, Node.js и другие компоненты.

Различия между окружениями сводятся преимущественно к конфигурационным значениям, которые могут передаваться через переменные окружения.

---

## 11. Logs — логи

Backend использует стандартный механизм логирования ASP.NET Core.

Логи выводятся в стандартный поток приложения и доступны через Docker:

```cmd
docker compose logs api
```

Для просмотра логов всех сервисов:

```cmd
docker compose logs
```

Логи не должны храниться внутри файловой системы контейнера как основной способ их хранения.

---

## 12. Admin Processes — административные процессы

Административные задачи отделены от основного API-процесса.

Применение миграций базы данных выполняется отдельным контейнером:

```text
TaskFlow.Migrations
```

При запуске Docker Compose:

1. PostgreSQL запускается и проходит healthcheck;
2. контейнер миграций подключается к PostgreSQL;
3. выполняются миграции;
4. после успешного завершения миграций запускается API.

Таким образом, изменение структуры базы данных не требует ручного выполнения SQL-команд внутри работающего API-контейнера.

---

# 5. Вывод

В результате был разработан клиент-серверный веб-сервис TaskFlow с frontend на Angular и backend на ASP.NET Core Web API.

Приложение использует PostgreSQL для хранения данных, предоставляет REST API и реализует CRUD-операции над основными сущностями.

Компоненты приложения контейнеризированы с использованием Docker и Docker Compose.

Архитектура и конфигурация приложения построены с учётом принципов Twelve-Factor App: зависимости объявлены явно, конфигурация отделена от кода, PostgreSQL используется как внешний сервис, процессы могут масштабироваться, приложение предоставляет порты самостоятельно, логи выводятся в стандартный поток, а административные операции вынесены в отдельный процесс миграций.
